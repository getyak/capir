# GET-51 settings implementation

## Outcome and boundary

Implement the approved GET-51 settings direction in the real authenticated Web workspace and signed macOS host. A user entering Settings from any supported entry reaches one predictable place; selecting a category shows a matching title and one content pane. Web retains its workspace shell, while macOS keeps a single independent native Settings window and locally available device controls. Search reaches the exact setting owner, appearance changes can be previewed and cancelled, and sources/action boundaries are described without inventing permissions or data counts.

This is application code and focused verification only. Do not change Figma, backend authorization, data collection, external effects, production credentials, deployment, or unrelated working-tree state. All relationship examples in tests or visual QA must be synthetic.

## Chosen approach

1. Keep one settings section schema and one content owner. Render the Web section nav inside the normal workspace; hide both Web section nav and workspace navigation reliably in the macOS Settings surface before the first meaningful paint. Match selected native section and content title, including invalid/fallback routes.
2. Give macOS one reusable Settings window for `⌘,`, toolbar, account menu, and contextual links. Keep `This Device` and Updates native and usable without the Web origin. A Settings link to a non-settings workspace destination must open the main workspace window at that destination rather than trapping the workbench inside the Settings window. Preserve account linking and other auth recovery routes.
3. Implement a real setting search on Web and macOS using indexed existing destinations. Include aliases such as screenshot/screen recording; expose exact scope/destination; support keyboard, empty results, Escape, and focus return. Do not search or reveal private relationship data.
4. Implement the visual structure with existing tokens: quiet rail, clear title, effective scope, source-to-proposal-to-action boundary, and restrained approval callout. Use only truthful states from existing services. Never show Figma's synthetic counts or imply an integration/permission is active without readback.
5. Make appearance preference changes previewable and cancellable, with system/light/dark choices only if persistence and system-following behavior are actually implemented. Show a synthetic sample and local-storage scope; preserve existing avatar behavior and account/security flows. Failures retain drafts.
